# Agent入门到工程化落地

## 一、Agent基础知识

### 什么是Agent

实现层：Agent = LLM + 上下文 + 工具

直觉层：大脑 + 眼睛 + 手脚

学术层：策略（Policy）、观察空间（Observation Space）与动作空间（Action Space）

**LLM 是 Agent 的大脑**，理解意图、思考规划、做出判断。

**上下文是 Agent 的眼睛**，是 Agent 在每个决策点收到并保留的信息表示

**工具是 Agent 的手脚**，Agent依赖工具来感知或者改变外部的接口



### LLM的数据来源

**预训练**所积累的世界知识与语言能力，以及**后训练**所固化的决策策略



### Agent交互的最小结构

![image-20260911161817927](C:\Users\11405\AppData\Roaming\Typora\typora-user-images\image-20260911161817927.png)

**Agent 与 Environment 是闭环交互的两方**。**环境**不断向 Agent **返回当前观察**，**Agent** 根据已有**上下文选择下一步行动**；行动改变环境状态，新的状态再产生下一次观察，**循环**由此继续。这是理解所有 Agent 交互的**最小结构**。

本节开头的工程公式可以据此重新展开：**LLM 对应 Model，“上下文 + 工具”构成最小 Harness**；生产系统还会在 Harness 中加入约束、验证和纠正。后文所有架构都遵循这条边界。



### 如何提升Agent的能力

观察通道与动作接口共同构成了 Agent 与外部环境之间的边界。在底层模型固定时，提升 Agent 任务表现最主要的系统工程手段，往往就是重新定义或扩展观察空间与动作空间。**就是扩展上下文和工具。**



### OpenClaw与普通Agent的区别：

拓展观察空间，对接消息渠道（WhatsApp、Telegram等）接收任务和返回结果，同时采用本地 Gateway，连接 Google Drive、Notion 等云应用以及本地文件系统。更多的数据整合在同一个观察空间中。

### 什么是工具？工具如何调用？

工具是Agent的手脚，Agent通过工具来修改、操作外部环境。

**工具调用**（Tool Calling，也称 Function Calling），模型能够通过结构化的方式调用外部工具。

工具调用流程：

​	声明：告诉模型有哪些工具， 工具的用途，需要传递的参数

​	决策：模型自主决策要不要调用工具、调用哪个、传什么参数

​	执行：工具提供方执行工具，返回执行结果

​	观察：结果被追加到上下文中，模型据此决定下一步行动

这个循环就是ReAct 的基础。



### 工具分类

**感知工具**让 Agent 能访问信息

**执行工具**让 Agent 改变外部

**协作工具**让 Agent 与其他 Agent 分工合作

**事件触发工具**不是 Agent 主动调用的，作为外部输入来驱动 Agent 开始执行任务。事件驱动、定时驱动、回调激活。事件适配器同样是 Environment 向 Agent 提供观察的通道。

**用户沟通工具**是 Agent 主动与用户建立连接、传递信息的渠道

**如何定义工具：通用工具用于组合与探索；专用工具用于约束高风险和强业务规则操作**。

### 上下文结构

**系统提示词**（System Prompt）：由开发者编写，在整个对话过程中保持不变，相当于 Agent 的“岗位说明书”——定义它的**身份、权限和行为准则**。系统提示词中还会包含跨会话保存的**用户记忆**（用户偏好、历史行为、背景设定等个性化信息）和动态注入的环境状态。

**工具定义**（Tool Definitions）：声明 Agent 可用工具的名称、功能描述和参数格式。是 Agent 行动能力的基础。缺失工具也会回答，基于预训练数据给出回答，可能存在幻觉。

**用户消息**（User Messages）：来自用户的输入。还可能包含通过 RAG动态检索引入的**外部知识**

**模型回复**（Assistant Messages）：模型之前生成的回复，最多包含三个部分——思考过程（`reasoning`，即内部思考链，用于保持思维的连贯性和决策的可解释性）、文本内容（`content`，即对用户的回复）和工具调用请求（`tool_calls`，即 Agent 采取行动的方式）。在一次具体的回复中，三者不一定同时出现：例如 Agent 决定调用工具时通常只有 `reasoning` + `tool_calls`，给出最终回答时通常只有 `reasoning` + `content`。

**工具执行结果**（Tool Results）：Agent 框架执行工具后返回的结果。这些结果是 **Agent 下一步思考的直接依据**，是闭环控制的关键，缺失它会让 Agent “盲目”执行，反复重试直到耗尽迭代预算。

（系统提示词 + 工具定义）是静态前缀，（用户消息 + 模型回复 + 工具执行结果）是随交互不断增长的动态消息历史**（轨迹）**。这五个部分共同构成了 LLM 每次推理时的上下文。**上下文决定了 Agent 能看到什么，而 Agent 只能基于它看到的信息做决策**。

**Agent 的上下文 = 静态前缀 + 轨迹**。



### ReAct **循环**

模型先**思考**当前应该做什么，然后调用工具**行动**，再**观察**工具返回的结果并继续思考下一步。循环步骤直到得到最终答案（当模型输出不再包含tools_call，则表示本轮结果为模型最终输出）。

示例：

![image-20260911180217213](C:\Users\11405\AppData\Roaming\Typora\typora-user-images\image-20260911180217213.png)

伪代码：

```
trajectory = [user_request]

repeat:
    context = stable_prefix + trajectory
    decision = Model(context)
    trajectory.append(decision)

    if decision has no tool call:
        return decision.answer

    for call in decision.tool_calls:       # independent calls may run in parallel
        validated_call = Harness.validate(call)
        observation = Environment.execute(validated_call)
        trajectory.append(observation)
```

运行轨迹：

```
轨迹 = [
  {role: "user" , content: "根据公司季度收入：Q1 2.5M 美元，Q2 2.1M 欧元，Q3 1.8M 英镑，Q4 380M 日元，计算公司年度总收入和季度平均收入" },

  # 第一次迭代 - LLM 看到上述轨迹，生成响应

   content: "" ,  # 没有直接回复用户

  # Agent 框架执行工具，添加结果到轨迹
  {role: "tool" , content: "EUR->USD: 2282608.7" },

  {role: "tool" , content: "JPY->USD: 2541806.02" },
```

### 什么是Harness

“模型即 Agent”（Model as Agent）这一新范式代表了 AI Agent 发展的最新方向。模型通过预训练开始将工具调用能力内化为原生能力，随着模型越来越强大，从而产生的**约束和引导模型的工程架构就是Harness**。在 Agent 中，Harness 包括上下文管理、工具接口、安全约束、验证与纠正等基础设施。当某些功能由模型决策时过于不稳定，就先由Harness实践，当模型内化了这部分能力，Harness就可以卸下这部分，转而兜底新的能力前沿。

从 Harness 工程的视角看，可以把 LLM 抽象为核心组件 Model，把 Agent 边界内负责支撑模型运行及模型与环境交互的代码、配置和服务统称为 Harness。

Harness 的核心是原公式中的“上下文管理 + 工具接口”，再加上三层保障机制：**约束**（限定 Agent 能做什么、不能做什么）、**验证**（检查 Agent 做得对不对）和**纠正**（做错了怎么补救）。

**Agent = Model + Harness**

**Harness = 上下文管理 + 工具接口 + 约束 + 验证 + 纠正**

**Harness 不是模型之外的一切**，而是 **Agent 边界内、模型之外**的运行与治理层。

围绕这些工具构建的保障机制才是真正的核心。这些机制包括：

- **流程状态管理**：追踪 Agent 当前执行到哪一步
- **多层上下文压缩**：当信息太多时自动精简
- **权限分类**：控制哪些操作需要用户确认
- **熔断器**（Circuit Breaker）：当错误连续发生时自动“断电”停止重试——就像家里电路短路时保险丝会自动跳闸，防止整个系统崩溃
- **错误恢复机制**：捕获异常、回滚到上一稳定状态、重试或交还给人类

**行业正在从“能做事”向“可靠地做事”转变，Harness 工程因此成为 Agent 系统的核心竞争力。**



### Agent工程范式的演进

**提示工程**：通过优化输入给模型的自然语言指令来提升输出质量。

**上下文工程**：系统性地管理模型能看到的所有信息（系统指令、工具定义、对话历史、外部知识）

**Harness 工程**：从“模型能看到什么”进一步扩展到“Agent 如何组织模型运行并与环境交互”，工具接口、约束机制、验证手段、反馈循环和错误恢复等 Agent 边界内、模型之外的运行与治理机制。

**Loop 工程**（Loop Engineering）：单次运行扩展到跨轮次的持续自主运转：谁来发现下一件该做的事、何时验证、何时才算真正完成

**Graph 工程**：描述一种更高层的编排视角：把 Agent 循环、确定性程序和人工审批组织成显式的执行图，其中节点承担具体能力，边规定路由与依赖，结构化状态沿边传递并在关键边界处持久化，Claude Code通过json的格式拆分任务规划Agent执行图



### 构建有效 Agent 的核心原则

**保持简单**：从最简单的方案开始，只在确实必要时才增加复杂度。首先考虑单个 LLM 调用。如果通过优化提示词和上下文示例就能解决问题，就不要引入 Agent 系统。

**保持透明**：明确显示 Agent 的规划步骤、执行日志和决策轨迹（可观测性）

**设计好工具接口**：设定好工具注释，防止AI调用错误

### 护栏与安全性

**护栏**：保障 Agent 行为安全可控的分层防线。人工授权、工具最小权限、提示注入防护、参数合法校验

上下文层护栏：

​	**规则驱动**——用自然语言写成的规则

​	**上下文联合判断**——把用户提问和模型回答放在一起检查

​	**两级筛查**——先用一个极轻量的探针（直接读取模型内部激活，几乎零成本）检查所有对话，发现可疑之处再交给更强的分类器复审，而不是直接拒绝。

**执行层**护栏:

​	**工具风险评级**：根据操作是否可逆、权限等级、财务影响，为每个工具标注风险等级（低/中/高），高风险操作需额外审查或人工确认。

​	**输出检查**： **PII 过滤器**审查输出中的个人身份信息，**输出验证**则通过内容检查确保回复与品牌价值一致。

**数据层**护栏：

​	与执行层类似，对数据操作时，重要数据交给一层稳定的、经过人类审查的机制强制执行：数据库的行级安全策略、约束与校验器、受控视图与存储过程，以及由受信任运行时绑定、无法被伪造的访问上下文。

高风险操作引入人工干预，需要授权的工具、需要授权的执行节点。**超过失败阈值** 为 Agent 的重试次数或操作次数设置上限。超限落入人工处理。

## 贯穿全书的设计模式

**提议者—审核者（Proposer-Reviewer）**：双边复核，产出与评判由两个不共享上下文的角色分别承担，评判方看到的是产物本身——渲染结果、测试输出、结构化的调用参数——而不是产出方的推理过程。它成立的前提是**自审不可靠**

**渐进式披露（Progressive Disclosure）**：不把全部信息一次性放进上下文，是先给一份可检索的目录，再按需加载细节。

**只增不改（Append-only）**：状态以追加的方式演进，已经写下的内容不再回头修改。换来的是可缓存、可重放、可审计。

**边界集 + 保留集（Boundary Set + Retention Set）**：任何一次修改都要同时在"它应当改变的那批样本"和"它不应当影响的那批样本"上验证。测试的正反案例以及回归测试

**最小 diff + 可回滚**：每次修改尽量小、带来源、可单独回滚，而不是整体重写。



### 思考题

1. ★★ 如果你只能给一个 Agent 系统增加一项能力——更强的模型、更丰富的上下文还是更多的工具——你会选哪个？在什么条件下你的选择会改变？

   首先增加的逻辑由简单到复杂，优先调整提示词，再到增加工具，再到更换模型。

   但是并不是一定如此，根据需要agent实现的功能来区分，需要agent按照指定格式输出，可以调整上下文增加输出schame；需要agent拥有查询互联网的能力，增加查询工具；如果需要agent支持图像识别的能力，就需要更换支持多模态的模型

2. ★★★ ReAct 循环中，累计缓存读取量随轮数近似二次方增长。如何降低这种增长？

   本质涉及到上下文记忆的处理，以及通过前缀缓存降低token消耗。首先静态前缀保持不变，系统提示词、工具信息等，后续用户会话，大模型回复在后方追加，包括输出schame也放在提示词最后。在这些的基础上再进行记忆处理，包括久远会话摘要，超长摘要提取事实落入长期记忆等操作。减少会话轮数。

3. ★★ “模型即 Agent” 范式意味着模型在工具调用决策上越来越自主。但本章论证了 Harness 工程的重要性反而在增加。这两个趋势如何共存？Agent 框架未来的核心价值体现在哪些方面？

   模型自主性越强，不确定性不稳定性程度越高。 Harness 工程的作用是对模型能力的约束、验证、纠正，降低Agent的不稳定性，确保项目可落地。**当各家模型的能力越来越接近、不再是决定性的差异因素时，竞争优势就转移到了模型之外的工程实践**。
